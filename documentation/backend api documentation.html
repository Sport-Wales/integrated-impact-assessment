Overview What the Backend Does

The IIA Portal backend is a set of Azure Functions — small, self-contained Node.js functions that each handle one specific API request. They sit inside the /api folder and are deployed automatically alongside the React frontend as part of the Azure Static Web App (SWA).

There is no traditional server running continuously. Each function wakes up when a request comes in, runs for milliseconds, and stops. Azure manages all scaling, availability, and infrastructure automatically.

Authentication How the Backend Knows Who You Are

Authentication is handled entirely by Azure SWA — the backend functions never touch passwords, tokens, or Microsoft login flows. By the time a request reaches a function, SWA has already verified the user's identity and injected it into the request as a header.

The x-ms-client-principal Header

On every authenticated request, SWA adds a header called x-ms-client-principal. It contains a base64-encoded JSON object with the user's identity from Azure AD. The getUser.js utility (located at api/src/utils/getUser.js, lines 15–43) decodes this header and returns a simple object:

// What getUser() returns (api/src/utils/getUser.js, line 15)
{
  userId:    "abc123def456...",          // Azure AD Object ID — stable, never changes
  userEmail: "anselm.powell@sport.wales" // always lowercased (line 35)
}

userId is used as owner_id in the database — it uniquely identifies a user even if their email changes. userEmail is used for sharing, display, and the @sport.wales validation.

Route Protection — staticwebapp.config.json

The app/staticwebapp.config.json file tells SWA to block all unauthenticated requests to /api/* before they ever reach a function:

{
  "routes": [
    { "route": "/api/healthCheck", "allowedRoles": ["anonymous"] },
    { "route": "/api/*",           "allowedRoles": ["authenticated"] }
  ],
  "responseOverrides": {
    "401": { "statusCode": 302, "redirect": "/.auth/login/aad" }
  }
}

If an unauthenticated request hits /api/*, SWA redirects to the Microsoft login page — the function never executes. This is why all functions set authLevel: 'anonymous' — they rely on SWA's routing layer, not Azure Functions' own auth.

Local Development Fallback

When running locally with swa start, SWA's auth header is not present. getUser.js (at api/src/utils/getUser.js, lines 20–26) detects this and returns a dummy user when NODE_ENV=development:

// Only when NODE_ENV=development (set in local.settings.json)
// api/src/utils/getUser.js, lines 20–26
{ userId: 'LOCAL_DEV_USER', userEmail: 'dev.user@sport.wales' }
Security

NODE_ENV=development is set only in local.settings.json, which is git-ignored and never committed. In production on Azure, this variable is not present — the fallback can never fire.

Database Layer db/index.js — The Only Way Functions Touch the Database

Every function accesses the database through one shared module: api/src/db/index.js. Functions never import database drivers directly — they call db.query() and get back an array of rows. This keeps every function simple and consistent.

How to Use It
// From any function file
const db = require('../db');

// SELECT — returns array of row objects (db/index.js, query() function, line 150)
const rows = await db.query(
  'SELECT id, title FROM assessments WHERE owner_id = $1',
  [user.userId]
);
// rows = [{ id: 'uuid...', title: 'Community Cycling' }, ...]

// INSERT with RETURNING — get the new row's ID
const result = await db.query(
  'INSERT INTO assessments (owner_id, title) VALUES ($1, $2) RETURNING id',
  [user.userId, 'My Assessment']
);
// result = [{ id: 'generated-uuid...' }]

// UPDATE — returns empty array (no rows returned)
await db.query(
  'UPDATE assessments SET status = $1 WHERE id = $2',
  ['complete', assessmentId]
);
Always use parameters

Never build SQL strings with template literals (e.g. `WHERE id = '${id}'`). Always use $1, $2, $3 placeholders with a params array. This prevents SQL injection attacks and is enforced across every existing function in api/src/functions/.

Connection Pooling

The database connection pool is created once and reused across all function invocations on the same Azure Functions instance. This pattern prevents the serverless function from opening a new database connection on every single request. Located at api/src/db/index.js, the `getConnection()` function (lines 23–114) manages this automatically.

The pool is configured with a maximum of 10 connections (line 98), a 30-second idle timeout (line 99), and a 10-second connection timeout (line 100). If the connection fails, the pool is cleared so the next call reconnects from scratch.

SSL is required for Azure PostgreSQL: ssl: { rejectUnauthorized: false } is set in the pool config (line 97). This encrypts the connection without requiring a CA certificate bundle to be bundled with the code.

Database Schema Tables, Columns, and Indexes

The schema is defined in api/src/db/schema.sql. There are two tables. The schema uses CREATE TABLE IF NOT EXISTS so it is safe to re-run — it will not destroy existing data.

Table 1 — assessments

One row per assessment. All form field answers are stored as a single JSONB column (form_data) rather than individual columns, because form questions evolve over time and JSONB is flexible without requiring schema migrations. Located at api/src/db/schema.sql, lines 27–94.

There is a UNIQUE constraint on (assessment_id, user_email). This prevents the same person being added twice and enables UPSERT — if you share with someone who already has access, shareAssessment updates their role instead of creating a duplicate row.

Permission Model Who Can Do What

Every function enforces its own permissions independently. There is no central middleware — each function fetches the assessment, checks ownership or the permissions table, and returns 403 if the user is not allowed. This makes each function self-contained and easy to audit.

There are three roles: owner (created the assessment), edit (shared with edit access), view (shared with read-only access). A signed-off (submitted) assessment blocks all writes regardless of role, with one deliberate exception: saveAssessment still accepts a request that carries reviewedAt, since the Final Review step has to save after submission by design — see the Review Availability section below.

How permission is checked in code
// Every function that checks permissions follows this pattern:
const rows = await db.query(
  'SELECT owner_id, status FROM assessments WHERE id = $1',
  [assessmentId]
);
if (rows.length === 0) return { status: 404, ... };

const isOwner = rows[0].owner_id === user.userId;
if (!isOwner) {
  const perm = await db.query(
    'SELECT role FROM assessment_permissions WHERE assessment_id = $1 AND user_email = $2',
    [assessmentId, user.userEmail]
  );
  if (perm.length === 0 || perm[0].role === 'view') {
    return { status: 403, jsonBody: { error: 'You do not have permission' } };
  }
}
Review Availability — frontend-computed, not enforced server-side

The Final Review step (Form1 Step 10 / Form2 Step 4) is meant to happen once the work has actually taken place, not immediately after submission. It stays locked until getReviewAvailability() in app/src/utils/reviewGate.js says it's due:

  • Never available before status = 'signed_off'
  • Otherwise available from whichever date the lead entered in the reviewDate field (Form1 Step 8 / Form2 Step 2) — or signed_off_at + 6 months if that field was left blank
  • Once due, it stays available indefinitely — there's no cutoff, so a late review can always still be added

This is a UI gate, not a database constraint: the backend's only involvement is the saveAssessment exception above (any request carrying reviewedAt is accepted regardless of date) and the review_date column added to listAssessments. Nothing stops a hand-crafted API call from saving a review early — the app trusts the frontend here the same way it already trusts frontend-enforced read-only fields elsewhere.

Frontend Connection How the Frontend Calls the Backend

The frontend never calls backend functions directly — all API calls go through app/src/services/api.js. This is the single layer between the React components and the backend. Every function in api.js maps to exactly one backend function.

The Frontend API Service Pattern
// Located at: app/src/services/api.js
export const apiService = {

  saveAssessment: async (formData) => {
    const response = await fetch('/api/saveAssessment', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(formData),
    });
    return await handleResponse(response); // throws on non-200
  },

  listAssessments: async () => {
    const response = await fetch('/api/listAssessments');
    return await handleResponse(response);
  },
};

The URL /api/saveAssessment is a relative path. In development (swa start), the SWA CLI proxies this to your local Azure Functions. In production on Azure, SWA routes it to the deployed functions automatically. No environment-specific URL configuration needed.

Error Handling Patterns

Two patterns are used deliberately. Most methods use Pattern A (throw user-friendly errors). Two methods use Pattern B (throw raw errors silently).

PatternUsed byWhy
Pattern A — handleError()getAssessment, listAssessments, completeAssessment, signOffAssessment, shareAssessment, getPermissions, removeShareThrows a user-friendly message. The UI surfaces this as an error notification.
Pattern B — raw throwsaveAssessment, deleteAssessmentCallers swallow the error silently. localStorage is always the source of truth — the DB save is best-effort background sync.

Azure Infrastructure How the Backend Lives on Azure

The backend runs entirely within Azure's managed services. There are no virtual machines to manage, no operating systems to patch, and no servers to maintain. Everything is PaaS (Platform as a Service) — Azure handles the infrastructure and you manage only the code and configuration.

Resource Group — rg-sportwales

A resource group is simply a folder in Azure that holds related resources together. Everything for the IIA portal lives inside rg-sportwales. You can find it by logging into portal.azure.com and searching for the resource group name.

Azure Static Web App — How the API Deploys

The SWA is connected to the GitHub repository. A GitHub Actions workflow file (.github/workflows/azure-static-web-apps-ashy-desert-065fb6403.yml) triggers automatically on every push to the dev branch. It builds the React frontend with Vite and deploys the Azure Functions from the /api folder. No manual deployment is ever needed.

The workflow is configured with three key paths:

app_location:    "/app"   # Where the React code lives
api_location:    "/api"   # Where the Azure Functions live
output_location: "dist"   # Where Vite puts the built frontend

SWA automatically routes any request to /api/* to the Azure Functions. Any other request serves the React app. They appear as one application to the user even though they are two separate things behind the scenes.

PostgreSQL Flexible Server — Azure Portal

The database server is managed entirely through the Azure Portal. You never SSH into it or manage the operating system. To view the database, connect using pgAdmin or Azure Data Studio with the credentials from local.settings.json.

In the Azure Portal, navigate to sw-iia-dev-db to find:

  • Overview — server hostname, status, and version
  • Databases — list and create databases (iia-dev-db)
  • Networking — firewall rules. "Allow Azure services" must be enabled so the SWA functions can reach the database.
  • Connection strings — pre-built connection strings with the hostname filled in
  • Backups — automatic daily backups with 7-day retention. Point-in-time restore available.
App Registration — Azure AD Authentication

The App Registration (Integrated Impact Assessment) in Azure Active Directory is what allows users to log in with their @sport.wales Microsoft accounts. It is managed through Azure Portal → App registrations.

The App Registration provides two values used in staticwebapp.config.json and SWA Configuration settings:

  • Application (client) ID — stored as AAD_CLIENT_ID in SWA Configuration
  • Directory (tenant) ID — used in the openIdIssuer URL in staticwebapp.config.json
  • Client secret value — stored as AAD_CLIENT_SECRET in SWA Configuration
Redirect URIs

The App Registration must have redirect URIs registered for each SWA URL. The format is: https://[swa-url].azurestaticapps.net/.auth/login/aad/callback. Without this, Microsoft will reject the login redirect with a "redirect URI mismatch" error.

Superuser Configuration — SUPER_USER

The SUPER_USER environment variable enables view-all access for specified Sport Wales staff (typically the project owner and developers). Superusers can view every assessment in the system but cannot edit, delete, or sign off assessments they don't own.

Local Development Setup

In local development, SUPER_USER is not set. Instead, a hardcoded array in api/src/utils/superusers.js is used:

// api/src/utils/superusers.js — lines 1-7
const LOCAL_SUPERUSERS = [
  'firstName1.LastName1@sport.wales',
  'firstName2.LastName2@sport.wales',
  'firstName3.LastName3@sport.wales',
];

To add or remove superusers locally, update this array. No restart needed.

Azure Deployment Setup (Dev and Production)

In Azure, set the environment variable in the SWA configuration:

  1. Log into portal.azure.com
  2. Go to Static Web Apps → select the SWA resource (e.g., sw-iia-dev)
  3. Click Configuration (left menu)
  4. Click Application settings
  5. Click + Add
  6. Enter:
    Name: SUPER_USER
    Value: userFirstName1.LastName1@sport.wales, userFirstName2.LastName2@sport.wales, userFirstName3.LastName3@sport.wales
  7. Click Save
How It Works

When a superuser logs in:

  1. listAssessments returns ALL assessments in the system, not just owned + shared ones
  2. For each assessment, user_role is computed: 'owner' if they own it, their explicit permission role if shared, otherwise 'view'
  3. When they open an assessment they don't own, it loads with user_role: 'view' — all form fields become read-only
  4. All write endpoints (save, delete, sign-off, complete) independently verify ownership and reject non-owners with 403
Implementation Detail

The superuser check happens in api/src/utils/superusers.js (line 36). The function isSuperUser(email) normalizes the email to lowercase and compares against the configured list. No other files need modification — the existing permission model automatically enforces read-only for superusers viewing shared assessments.

Scaling the Backend How to Add a New API Function

When new requirements come in that need a new backend capability, follow the established pattern exactly. Every existing function is a reference implementation — read one or two before writing your own.

The Standard Function Template

Create a new file in api/src/functions/. The filename becomes the URL path — myNewFunction.js → /api/myNewFunction.

// api/src/functions/myNewFunction.js
// One-line description of what this function does.
//
// Called by: [which frontend component calls this]
// Returns:   [what the response body contains]
// Allowed:   [who can call this — owner / editor / viewer]

const { app }     = require('@azure/functions');
const db          = require('../db');
const { getUser } = require('../utils/getUser');
const logger      = require('../utils/logger');

app.http('myNewFunction', {
  methods: ['POST'],          // GET for reads, POST for writes
  authLevel: 'anonymous',     // always anonymous — SWA handles auth at routing level
  handler: async (request, context) => {
    logger.setContext(context);

    // 1. Get user identity — always the first step
    const user = getUser(request);
    if (!user) {
      return { status: 401, jsonBody: { error: 'Unauthorised' } };
    }

    // 2. Parse body (POST only)
    let body;
    try {
      body = await request.json();
    } catch {
      return { status: 400, jsonBody: { error: 'Invalid JSON body' } };
    }

    // 3. Validate required fields
    const { assessmentId } = body;
    if (!assessmentId) {
      return { status: 400, jsonBody: { error: 'assessmentId is required' } };
    }

    try {
      // 4. Fetch the assessment to check ownership and status
      const rows = await db.query(
        'SELECT owner_id, status FROM assessments WHERE id = $1',
        [assessmentId]
      );
      if (rows.length === 0) {
        return { status: 404, jsonBody: { error: 'Assessment not found' } };
      }

      // 5. Check permission
      if (rows[0].owner_id !== user.userId) {
        return { status: 403, jsonBody: { error: 'Only the owner can do this' } };
      }

      // 6. Perform the database operation
      await db.query(
        'UPDATE assessments SET some_column = $1 WHERE id = $2',
        ['some_value', assessmentId]
      );

      logger.info(`myNewFunction: ${assessmentId} by ${user.userEmail}`);
      return { status: 200, jsonBody: { success: true } };

    } catch (error) {
      logger.error('myNewFunction error:', error.message);
      return { status: 500, jsonBody: { error: 'Failed to do the thing' } };
    }
  }
});

If You Need a New Database Column

If your new function needs to store a new piece of data that doesn't fit in the existing form_data JSONB column, you need to add a column to the schema. Update api/src/db/schema.sql and run the following in pgAdmin against iia-dev-db:

ALTER TABLE assessments ADD COLUMN IF NOT EXISTS my_new_column TIMESTAMPTZ;
Update schema.sql too

Always add the new column to schema.sql as well, not just run the ALTER TABLE. The schema.sql file is the source of truth — it is what you would run to recreate the database from scratch on a new environment.

If the Data Fits in form_data

If the new data is simply a new form field answer, you do not need a new column or function. The form_data JSONB column is flexible — just add the field to FormContext.jsx's getInitialState() and the saveAssessment function will store it automatically as part of cleanFormData.

Only create a dedicated column when the data needs to be: queried or filtered directly in SQL, displayed in the workspace table without loading full form_data, or used for access control or audit purposes.

Checklist Before Deploying a New Function
  • File is in api/src/functions/ and follows the standard template
  • authLevel: 'anonymous' is set — never use 'function' or 'admin'
  • User identity is checked as the very first step
  • All SQL queries use $1, $2 parameters — no string interpolation
  • Ownership or permission is verified before any write operation
  • A corresponding method is added to api.js in the frontend
  • If a new DB column is needed, schema.sql is updated and the column is added via ALTER TABLE on dev
  • Function is tested locally with swa start before pushing
Troubleshooting Common Issues and How to Fix Them
API call returns 401 on the deployed SWA

The user's session has expired or the SWA auth configuration is incorrect. Check that AAD_CLIENT_ID, AAD_CLIENT_SECRET, and the Tenant ID in staticwebapp.config.json are all correct. Also check that the SWA URL is registered as a redirect URI in the App Registration.

Database connection fails on Azure

Check two things in the Azure Portal: (1) the DB_CONNECTION_STRING value in sw-iia-dev Configuration settings is correct, and (2) the PostgreSQL server's Networking settings have "Allow Azure services and resources to access this server" enabled. Without this checkbox, the SWA functions cannot reach the database even though they are in the same Azure subscription.

Function works locally but fails on Azure

The most common cause is a missing environment variable in the SWA Configuration settings. The variables in local.settings.json are local-only — they must also be added to Azure Portal → sw-iia-dev → Environment variables for the deployed version to read them.

saveAssessment stores unexpected fields in form_data

If new fields are added to FormContext state that should not be stored in the database, they must be explicitly destructured and discarded in saveAssessment.js before the ...cleanFormData spread. Check the destructuring block at the top of the handler — any field not listed there will end up in cleanFormData and be stored in the JSONB column.

getAssessment returns stale completedSteps

completedSteps is stored as a dedicated column in the database but FormContext reads it from inside form_data. The getAssessment function injects completed_steps back into form_data before returning. If the progress bar is loading incorrectly, check that this injection is present in getAssessment.js.

reviewed_at is not updating in the database

Step 10 and Form2/Step4 include reviewedAt: new Date().toISOString() in their save payload. If this field is missing from the payload, saveAssessment receives null for reviewedAt and the COALESCE keeps the existing value. Check that both step files include reviewedAt in their updatedData object passed to commitStep.
