Context What is the Integrated Impact Assessment (IIA)?

The Integrated Impact Assessment is a framework used by Sport Wales to evaluate the impact of policies and programmes on society. It assesses how a new initiative or change affects different groups, identifies risks and opportunities, and ensures informed decision-making.

This portal provides a digital tool for completing and managing IIAs. Users fill out detailed forms (Form 1 for full assessments, Form 2 for shorter ones), save their work, collaborate with colleagues by sharing assessments, and generate professional reports for review and sign-off.

Key User Roles

Owner: Person who created the assessment — can edit, share, complete, and sign off. Editor: Person with edit access — can save changes and complete but cannot sign off or share. Viewer: Person with view-only access — can read but cannot make changes.

Create or Open an Assessment

Two paths: New — click "Start New Assessment," choose Form Type (Full or Short), answer pre-form questions. Existing — click a row to open it (if you have access).

Opening an existing assessment calls apiService.getAssessment(id) which fetches the full assessment from the database. The form loads into FormContext (the app's central state manager at app/src/context/FormContext.jsx, lines 1–450) and renders the first step of the form.

Save & Move Forward

When the user clicks "Next" or the "Save" button (SaveButton.jsx at app/src/components/ui/SaveButton.jsx line 1), two things happen: (1) localStorage is already up-to-date from keystroke-by-keystroke syncing, and (2) the app calls apiService.saveAssessment(formData) to push the data to the database. If it's the first save, the backend returns a UUID which becomes the assessment's permanent ID. On subsequent saves, it's an UPDATE.

How it looks in code:

// SaveButton.jsx line 22 — when user clicks Save
const handleSave = async () => {
  setSaving(true);
  try {
    const result = await apiService.saveAssessment(formData);
    // result = { id: "new-uuid" } on first save, or { id: existing-uuid } on update
    updateFormData({ assessmentId: result.id });
  } catch (err) {
    console.error('Save failed:', err);
  }
  setSaving(false);
};

// Similarly in Form1/Step1.jsx line 50 — when user clicks Next:
const handleNext = async () => {
  setLoading(true);
  updateFormData({ form1: { ...formData.form1, title: formState.title } });
  await apiService.saveAssessment(formData); // Fire-and-forget
  navigate('/form1/step2');
};

This is fire-and-forget: the app doesn't wait for the backend response. The user sees the next step immediately, and localStorage already has their data, so nothing is lost if the save fails.

Complete & Sign Off

After all steps are filled, the user clicks "Mark as Complete" (Form1 Step 8, Form 2 Step 2) which calls apiService.completeAssessment(id). Later, in the Assessment Document view (AssessmentDocument.jsx at app/src/pages/AssessmentDocument.jsx line 1), the owner can click "Sign Off" which calls apiService.signOffAssessment(id), permanently locking the assessment as read-only.

Share & Collaborate

The owner can click the "Share" button (on any form step or the workspace) to open ShareModal (ShareModal.jsx at app/src/components/ui/ShareModal.jsx line 1). They type a colleague's email, choose "View" or "Edit" access, and click "Save permissions." This calls apiService.shareAssessment(id, email, role) which adds a row to the database's assessment_permissions table and generates a shareable link.

Hub The Workspace Table
Access Denied popup — Read state, show modal:

The workspace (LandingPage.jsx, lines 1–361) shows a table of assessments with columns: Title, Lead Person, Form Type, Status (Draft / Complete / Signed Off), Created, Last Updated, and Review. All assessments shown here have been retrieved from the database via apiService.listAssessments().

Why Two Tables?

The database query for listAssessments uses UNION to return both owned assessments and shared ones in a single table. The computed user_role field tells the UI whether the user is owner, editor, or viewer, so permission-sensitive buttons can hide themselves accordingly.

Critical Feature How Save Works — Three-Layer Safety

The save system is designed so users never lose data, even if the network fails or they close the browser mid-session. It has three layers: localStorage (instant), FormContext state (in-memory), and the database (persistent).

Layer 1: Keystroke-by-Keystroke to localStorage

Every time a user types in a form field, the input handler in the step file calls updateFormData(section, newValue) (FormContext.jsx line 162). This updates FormContext state immediately. A useEffect hook (FormContext.jsx lines 86–91) watches FormContext and automatically writes the entire state to localStorage whenever it changes. The `writeAssessmentToStore()` function handles the write (FormContext.jsx, around line 34).

This means: type 5 characters → localStorage updates 5 times with all 5 keystroke states. If the user closes the browser without clicking "Next" or "Save," all their typed data is safe in localStorage.

How it works:

// FormContext.jsx lines 86–91 — the auto-sync hook
useEffect(() => {
  if (formData.localId) {
    writeAssessmentToStore(formData.localId, formData);
  }
}, [formData]); // Runs every time formData changes

// writeAssessmentToStore (line 34) — writes to localStorage
const writeAssessmentToStore = (localId, snapshot) => {
  const store = readAssessmentsStore();
  store[localId] = { ...snapshot, lastSavedAt: new Date().toISOString() };
  localStorage.setItem('iia_assessments', JSON.stringify(store));
};
Layer 2: On Navigation or Save Button

When the user clicks "Next" (in a step file) or "Save" (SaveButton.jsx), the app calls apiService.saveAssessment(formData) which sends the full FormContext state to the backend. The backend INSERT or UPDATE the assessment in the database.

This is NOT synchronous; it's fire-and-forget. The app navigates immediately (user sees the next step), and the database save happens in the background. If the save fails silently, localStorage already has the data, so it's not lost.

Layer 3: Reconciliation on Page Refresh

When the user returns to their workspace and reopens an assessment, UrlAssessmentLoader (App.jsx lines 39–75) fetches the data from the database. FormContext's loadAssessment() function (FormContext.jsx lines 295–361) compares timestamps: if localStorage has a newer lastSavedAt than the database's updated_at, it means the user typed unsaved changes. The function keeps localStorage data and fires a background sync (lines 355–360) to push it to the database silently using `apiService.saveAssessment(syncPayload)`.

Result: even if a background save failed before, this reconciliation ensures the database catches up.

How reconciliation logic works:

// FormContext.jsx lines 295–361 — inside loadAssessment()
const useLocalData = false;
let localSnapshot = null;

if (isDbBacked && dbResponse.updated_at) {
  const store = readAssessmentsStore();
  const existing = store[activeLocalId];
  if (existing?.lastSavedAt) {
    const localTime = new Date(existing.lastSavedAt).getTime();
    const dbTime = new Date(dbResponse.updated_at).getTime();
    if (localTime > dbTime) {
      useLocalData = true;  // localStorage is newer!
      localSnapshot = existing;
    }
  }
}

// If useLocalData = true, keep localStorage + background sync to DB
if (useLocalData && localSnapshot) {
  const shouldSync = !!localSnapshot?.assessmentId;
  if (shouldSync) {
    // Line 355–360 — fire-and-forget background sync
    apiService.saveAssessment(syncPayload).catch(err =>
      console.warn('[Reconciliation] Background sync failed:', err.message)
    );
  }
}
Why This Design?

Most save failures are transient (network blip, cold-start delay). By using localStorage as the source of truth, the app is resilient — the user sees instant feedback (data is safe), while the database sync happens asynchronously. This is why we never block navigation waiting for the backend to respond.

Collaboration How Share Works — Permissions & Shareable Links

Only the owner of an assessment can share it. Editors and viewers cannot share, even if they have edit access. The share button appears in two places: in the header on any form step (ShareButton.jsx at app/src/components/ui/ShareButton.jsx, line 1) and in the workspace table for each assessment row (LandingPage.jsx, line 302).

Step 1: Opening the Share Modal

When the owner clicks "Share," ShareButton checks if the assessment is already saved to the database. If yes, it opens ShareModal immediately with the assessment ID. If not (brand new assessment), it calls saveAssessment() first (ShareButton.jsx lines 21–34) to get the assessment ID, then opens the modal.

Step 2: The Share Modal Interface

ShareModal (at app/src/components/ui/ShareModal.jsx, lines 1–285) shows: a text field to enter a colleague's email, a dropdown to choose "View only" or "Can edit" access level, and an "Add" button. Below that is a table of everyone who already has access. At the bottom are two buttons: "Copy link" and "Save permissions."

Email Validation

Only @sport.wales email addresses are accepted. ShareModal validates this at line 79 with isValidSwEmail(). If someone enters an external email, ShareModal shows "Only Sport Wales accounts can have access."

Step 3: Staging & Submitting

When you add a colleague, ShareModal doesn't immediately call the backend. Instead, it "stages" the change in local state (setPendingAdds, line 82). You can add multiple people, remove them from the list, or change their access level — all without calling the backend. When you click "Save permissions," all staged changes are submitted at once via apiService.shareAssessment() (ShareModal.jsx line 107).

This two-phase approach lets you make bulk changes efficiently instead of making individual API calls per person.

How staging works:

// ShareModal.jsx line 82 — add a colleague to staging (no backend call)
const handleAdd = () => {
  const newPermission = { user_email: email.trim().toLowerCase(), role };
  setPendingAdds([...pendingAdds, newPermission]);
  setEmail('');
  setRole('view');
};

// ShareModal.jsx line 107 — submit all staged changes at once
const handleSavePermissions = async () => {
  setSubmitting(true);
  try {
    // Loop through all pending adds and make API calls
    for (const perm of pendingAdds) {
      await apiService.shareAssessment(assessmentId, perm.user_email, perm.role);
    }
    // ... handle removes similarly ...
    setPendingAdds([]);
    setPendingRemoves([]);
  } finally {
    setSubmitting(false);
  }
};
Step 4: The Shareable Link

When the owner clicks "Copy link," the link is built dynamically at ShareButton.jsx line 76 using the assessment ID and form type: ${origin}/${formType}/step1?id=${assessmentId}. For example: https://ashy-desert-065fb6403.7.azurestaticapps.net/form1/step1?id=abc123-def456...

The link always points to step 1 of the correct form, and includes the assessment UUID as a query parameter so the recipient's browser knows which assessment to load.

Step 5: What Happens When a Colleague Opens the Link

When the colleague clicks the shareable link (e.g., from an email), their browser navigates to that URL. UrlAssessmentLoader (App.jsx lines 39–75) detects the ?id= query parameter and fetches the assessment from the database using fetch('/api/getAssessment?id=...') at line 52.

If they have permission (owner, editor, or viewer), the assessment loads and the form renders. If they don't have permission, the backend returns a 403 status code. UrlAssessmentLoader catches this at line 55, redirects to the workspace, and passes the assessment title via React Router state. LandingPage (line 372) displays a friendly popup: "You don't have access to Community Cycling Programme. Please contact the assessment owner to be granted access."

Permission Levels

Owner: Full control — can edit, complete, sign off, delete, and share. Editor: Can edit and complete, but cannot sign off or re-share. Viewer: Read-only — cannot make any changes.

Deep Dive How localStorage Keeps Data Safe During Network Issues

The app uses localStorage as a local copy of the assessment. Every keystroke updates localStorage so the user never loses typed data, even if the network is down or the page closes. The database is a secondary backup that syncs whenever possible.

The Auto-Sync Cycle

FormContext has a useEffect hook (lines 86–91) that watches the formData state. Every time formData changes, it calls writeAssessmentToStore() which writes the entire form state to localStorage with a timestamp lastSavedAt. This happens ~every keystroke.

Database Sync on Navigation

When the user clicks "Next" or "Save," the step file calls apiService.saveAssessment(formData). This sends localStorage data to the backend, which performs an INSERT (new assessment) or UPDATE (existing). If the save succeeds, the database now has the latest data. If it fails silently, localStorage still has it.

The Reconciliation Process on Reopen

When the user closes the browser and later opens the assessment again, `loadAssessment()` (FormContext.jsx lines 102–171) compares `localStorage.lastSavedAt` vs `database.updated_at`. If localStorage is newer, it means the user made unsaved changes. The function keeps the localStorage data and fires a background sync (lines 165–170) to push it to the database silently. The user sees their data immediately and the database catches up.

Why Two Sources of Truth?

localStorage is fast (instant writes), survives network failures, and works offline. The database is persistent and shared. By syncing both, we get resilience (localStorage) + collaboration (database). If the backend is temporarily unavailable, users can still work and their data is safe. When they reconnect, the data syncs automatically.
