Before You Start Deep-Dive Glossary of Concepts

Before writing any code, you must understand the infrastructure you are building.

Azure Static Web Apps (SWA)

SWA is not just a hosting platform — it is an "Orchestrator". In a traditional setup, you rent a server for your React app, rent a different server for your Express API, and configure massive security rules so they can talk. SWA takes your GitHub repository, reads the /app folder (Frontend), reads the /api folder (Backend), hosts them under the exact same domain (e.g. sportwales.com/ and sportwales.com/api), and automatically handles the security handshake between them.

Managed Functions (Azure Functions)

This is the replacement for Express.js. An Express server stays "awake" 24/7, costing money and requiring maintenance. Managed Functions are "Serverless." When you write a Managed Function it is completely asleep (costing £0) until a user clicks "Submit". It wakes up in milliseconds, processes the data, saves it to the database, and immediately goes back to sleep.

Base64 Identity Scrambling

When a user logs in via Sport Wales Azure AD, Azure intercepts that login. Instead of forcing you to write complex token-validation logic, Azure confirms the user is valid, bundles their name and ID into a string of text, scrambles it using Base64 encoding, and attaches it as a hidden header (x-ms-client-principal) to every API request. Your backend script only has to unscramble it to securely know who is saving the form.

Single Page Application (SPA) Routing

Your React application is an SPA. This means it only generates one physical file: index.html. Pages like /form1/step3 do not actually exist as folders on a server — React fakes them in the browser using JavaScript. The backend must be explicitly told to route all traffic back to index.html, otherwise if a user hits "refresh" the server will look for a folder named step3, fail, and throw a 404 error.

Connection Pooling

Instead of opening a new database connection for every single request (which would quickly overwhelm the database), connection pooling creates a "pool" of 10 reusable connections. When a request needs the database, it borrows a connection from the pool, uses it, and returns it. This is critical for serverless functions because hundreds of simultaneous users would otherwise create hundreds of database connections.

6.1
Create Database Connection Manager (/api/src/db/index.js)

This is the only file that functions import for database operations. It creates a connection pool and provides a simple query() function that works with both database types.

How connection pooling works:

  • First request: Creates pool of 10 database connections, stores in memory
  • Second request: Reuses existing pool (fast!)
  • 100 concurrent requests: All share the same 10-connection pool — database not overwhelmed
Critical Bug Fixed
The original code checked if (pool && pool.connected) but PostgreSQL's pg library does not have a .connected property. This caused a NEW pool to be created on EVERY request, defeating connection pooling entirely. Fixed by checking database type first:
if (pool) {
  const dbType = process.env.DB_TYPE || 'postgres';
  if (dbType === 'postgres') {
    return pool; // PostgreSQL pool is always ready once created
  } else if (dbType === 'sql' && pool.connected) {
    return pool; // SQL Server requires .connected check
  }
}
⚠ Action Required Before Azure Deployment
The current pool config in db/index.js does not yet have an SSL setting. Azure Database for PostgreSQL enforces SSL on all connections — without this the database will refuse to connect in production. Add ssl: { rejectUnauthorized: false } to the pool config: 
pool = new dbClient({
  connectionString,
  max: 10,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 10000,
  ssl: { rejectUnauthorized: false }  // ← ADD THIS LINE before deploying to Azure
});
Why rejectUnauthorized: false: Azure PostgreSQL uses a self-signed certificate chain. This tells the pg driver to accept it without verifying against a local CA bundle. Standard and safe for Azure PostgreSQL.

Usage in any function file:

const db = require('../db');

// Simple query - the db module handles everything:

  'SELECT * FROM assessments WHERE id = $1',

6.4
Create Database Schema File (/api/src/db/schema.sql)

This SQL file must be created and run once against the Azure PostgreSQL database before any endpoint will work. Without it the database has no tables and every API call will fail with a "relation does not exist" error.

When to run it: Once Matt hands over the DB_CONNECTION_STRING, run this file against the database using pgAdmin, Azure Data Studio, or the psql CLI.

-- Run once against Azure PostgreSQL
-- Tool: pgAdmin, Azure Data Studio, or psql

CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE assessments (
  id                UUID          DEFAULT gen_random_uuid() PRIMARY KEY,
  owner_id          VARCHAR(255)  NOT NULL,
  owner_email       VARCHAR(255)  NOT NULL,
  form_type         VARCHAR(10)   NOT NULL CHECK (form_type IN ('form1','form2')),
  title             VARCHAR(500),
  lead_name         VARCHAR(255),
  status            VARCHAR(20)   NOT NULL DEFAULT 'draft'
                    CHECK (status IN ('draft','complete','signed_off')),
  form_data         JSONB         NOT NULL DEFAULT '{}',
  completed_steps   JSONB         NOT NULL DEFAULT '[]',
  created_at        TIMESTAMP     NOT NULL DEFAULT NOW(),
  updated_at        TIMESTAMP     NOT NULL DEFAULT NOW(),
  completed_at      TIMESTAMP,
  signed_off_at     TIMESTAMP,
  signed_off_by     VARCHAR(255)
);

CREATE TABLE assessment_permissions (
  id             UUID         DEFAULT gen_random_uuid() PRIMARY KEY,
  assessment_id  UUID         NOT NULL REFERENCES assessments(id) ON DELETE CASCADE,
  user_email     VARCHAR(255) NOT NULL,
  role           VARCHAR(10)  NOT NULL CHECK (role IN ('view','edit')),
  granted_at     TIMESTAMP    NOT NULL DEFAULT NOW(),
  UNIQUE (assessment_id, user_email)
);

-- Indexes
CREATE INDEX idx_assessments_owner_id   ON assessments (owner_id);
CREATE INDEX idx_assessments_status     ON assessments (status);
CREATE INDEX idx_assessments_updated    ON assessments (updated_at DESC);
CREATE INDEX idx_permissions_email      ON assessment_permissions (user_email);
CREATE INDEX idx_permissions_assessment ON assessment_permissions (assessment_id);
✓ Run Once
Run this script once. The ON DELETE CASCADE constraint on assessment_permissions means all permission rows are automatically cleaned up if an assessment is ever deleted.

Update App.jsx Wrapper StructureLocation: /app/src/App.jsx

Wrapped the entire app with <AuthProvider>. The order is critical:

<AuthProvider>          {/* Authentication FIRST  */}
  <FormProvider>        {/* Form state SECOND     */}

Backend Endpoint B11: Create deleteAssessment.js Endpoint ⏳ Pending

File: New file api/src/functions/deleteAssessment.js

URL: POST /api/deleteAssessment  |  Auth: function

Why it's needed: The frontend's api.js already calls POST /api/deleteAssessment — the frontend deletes local drafts immediately via deleteLocalAssessment() and then tries to sync the deletion to the database in the background. Without this endpoint, that background call will fail silently (which is safe by design) but the DB record will never be cleaned up.

What it does: Permanently deletes an assessment row from the database. Only the owner can call this. The frontend always removes from localStorage first — this DB delete is best-effort background sync.

Note on error handling
This endpoint uses Pattern B (silent fail) — the same pattern as saveAssessment. The caller in the frontend swallows the error silently because deleteLocalAssessment() already removed it from localStorage before the DB call is made.

Full file:

const { app } = require('@azure/functions');
const db = require('../db');
const logger = require('../utils/logger');

function getUser(request) {
  const header = request.headers.get('x-ms-client-principal');
  if (!header) return null;
  try {
    return JSON.parse(Buffer.from(header, 'base64').toString('utf8'));
  } catch { return null; }
}

app.http('deleteAssessment', {
  methods: ['POST'],
  authLevel: 'function',
  handler: async (request, context) => {
    logger.setContext(context);

    const user = getUser(request);
    if (!user) return { status: 401, jsonBody: { error: 'Unauthorised' } };

    const { assessmentId } = await request.json();
    if (!assessmentId) {
      return { status: 400, jsonBody: { error: 'Missing assessmentId' } };
    }

    try {
      // Only the owner can delete — backend enforces this
      const ownerCheck = await db.query(
        `SELECT id FROM assessments WHERE id = $1 AND owner_id = $2`,
        [assessmentId, user.userId]
      );

      if (ownerCheck.length === 0) {
        return { status: 403, jsonBody: { error: 'Only the owner can delete this assessment' } };
      }

      // ON DELETE CASCADE on assessment_permissions means
      // all permission rows are automatically removed too
      await db.query(
        `DELETE FROM assessments WHERE id = $1`,
        [assessmentId]
      );

      logger.info('Assessment deleted:', assessmentId);
      return { status: 200, jsonBody: { success: true } };

    } catch (error) {
      logger.error('deleteAssessment error:', error.message);
      return { status: 500, jsonBody: { error: 'Failed to delete assessment' } };
    }
  }
});

Reference Troubleshooting Common Issues
Cannot find module 'pg' when starting backend
Cause: Database drivers not installed
cd api
npm install
Health check returns "DB_CONNECTION_STRING not configured"
Cause: Expected — database credentials not yet provided by Matt

This is normal until Matt provides database credentials. Health check will show "unhealthy" until then. No action needed.

React app shows blank page
Cause: Multiple possible causes
  1. Check console for errors (F12 in browser)
  2. Verify npm run dev shows no build errors
  3. Check vite.config.js exists and has proxy configuration
  4. Try clearing browser cache (Ctrl+Shift+Delete)
swa: command not found
Cause: SWA CLI not installed globally
npm install -g @azure/static-web-apps-cli
Backend returns CORS errors in console
Cause: Vite proxy not configured OR backend not running
  1. Verify /app/vite.config.js has proxy configuration
  2. Make sure backend is running: cd api && npm start
  3. Or use swa start instead — handles routing automatically
Port 7071 already in use
Cause: Azure Functions already running in another terminal

netstat -ano | findstr :7071
taskkill /PID [number] /F

# Mac/Linux:
lsof -ti:7071 | xargs kill

  1. Check GitHub repo → Actions tab → Verify workflow exists

  3. Matt must connect Azure Static Web App to GitHub — this auto-creates the token
