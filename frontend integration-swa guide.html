Critical Concept Three Development Modes — Understand These First

The app behaves differently depending on how you start it. You must understand all three modes before working on the frontend.

Mode 1 — Pure Local  npm run dev
  • React only, runs on port 5173
  • Mock authentication via .env.local — no real login needed
  • API calls proxied to port 7071 via vite.config.js
  • When to use: UI work, styling, layout, component testing
Mode 2 — Full Stack  swa start
  • SWA CLI runs on port 4280 and coordinates React (5173) + API (7071)
  • Simulates Azure environment — mock Azure AD login available
  • Tests real frontend-to-backend communication flow
  • When to use: Testing complete flows, verifying API calls, demonstrating to stakeholders
Mode 3 — Azure Production
  • Everything hosted on Azure — real authentication and real database
  • sw-iia-dev — staging, safe test data, connected to develop branch
  • sw-iia-live — production, real staff data, connected to main branch
  • When to use: After local testing passes, real deployment
Deployment flow: git push develop → auto-deploys to sw-iia-dev → test → create PR → merge to main → auto-deploys to sw-iia-live
Section A Configuration Files ✓ Completed
A1
Vite Proxy ConfigurationFile: /app/vite.config.js

When running npm run dev, React is on port 5173 but the API is on port 7071. Without this proxy, any call to /api/hello would look for it at localhost:5173/api/hello — wrong port. The proxy secretly forwards it to port 7071.

import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:7071',  // Forward to Azure Functions
        changeOrigin: true,               // Prevents CORS errors
        secure: false                     // Allows HTTP locally
      }
    }
  }
})
Note
This proxy only applies during npm run dev. When using swa start, the SWA CLI handles routing. In Azure production, SWA handles it automatically. This file does nothing in production.

Section B Authentication System ✓ Completed
B1
How Azure SWA Authentication Works

Azure SWA handles the actual login process. React does not manage passwords or tokens directly.

1. User clicks "Login" 2. App redirects to /.auth/login/aad 3. Azure intercepts → shows Microsoft login page 4. User enters Sport Wales credentials 5. Azure validates with Sport Wales Azure AD 6. Azure redirects back to the app 7. Azure makes user info available at /.auth/me 8. AuthContext.jsx reads /.auth/me → user is now logged in

Three authentication scenarios depending on environment:

ScenarioHow it worksWhen
Mock AuthVITE_USE_MOCK_AUTH=true creates a fake user — no login screen needednpm run dev
SWA CLI Mockswa start provides a fake login form at /.auth/login/aadswa start
Real Azure ADActual Sport Wales Microsoft login with real credentialsAzure production
B2
AuthContext.jsx — Authentication State ManagementFile: /app/src/context/AuthContext.jsx

Fetches the logged-in user from Azure and makes that information available to every component in the app via the useAuth() hook.

What it provides:

ValueTypeDescription
userobject | nullContains userId, userDetails (email), userRoles
loadingbooleanTrue while the auth check is in progress
errorstring | nullError message if auth check failed
isAuthenticatedbooleanShorthand: !!user
login()functionRedirects to /.auth/login/aad (or mock in dev)
logout()functionRedirects to /.auth/logout (or mock in dev)

Usage in any component:

import { useAuth } from '../context/AuthContext';

function MyComponent() {
  const { user, loading, isAuthenticated, login, logout } = useAuth();

  if (loading) return <div>Checking login status...</div>;

  if (!isAuthenticated) {
    return <button onClick={login}>Log In</button>;
  }

  return (
    <div>
      <p>Welcome, {user.userDetails}!</p>
      <button onClick={logout}>Log Out</button>
    </div>
  );
}

How mock vs real auth is switched:

// Inside AuthContext.jsx — reads the environment variable
const useMockAuth = import.meta.env.VITE_USE_MOCK_AUTH === 'true';

// If mock: sets a fake user immediately, no network call
// If real: fetches /.auth/me from Azure SWA
B3
App.jsx — Provider Wrapping OrderFile: /app/src/App.jsx

The entire app is wrapped with AuthProvider so every component can access the logged-in user. The order matters.

<AuthProvider>        {/* Outermost — authentication state */}
  <FormProvider>      {/* Can access auth data when saving */}
    <Router>          {/* Can access both auth and form data */}
      <Routes>
        {/* All form steps, pages, routes */}
      </Routes>
    </Router>
  </FormProvider>
</AuthProvider>
Why order matters
AuthProvider must be outermost so FormProvider can access user identity when saving data (e.g. "save this form for user X"). If FormProvider came first, it would have no access to auth data.

Two error-handling patterns are used deliberately:

Pattern A — User-facing error (most methods)
Wraps in try/catch and throws a user-friendly message. Callers surface this to the UI. Used when a failure should be visible to the user.
Pattern B — Silent fail (saveAssessment, deleteAssessment)
Throws the raw error. Callers swallow it silently. Used because localStorage is always the source of truth — the DB save is a best-effort background sync. The user never sees a failure.

User-facing error messages by HTTP status:

401  →  "You must be logged in to do this"
403  →  "You do not have permission to do this"
404  →  "Assessment not found"
500  →  "Server error. Please try again."
other → "{context} failed. Check your connection."

Using saveAssessment — the most common call:

// formData must include assessmentId:
//   null   = new assessment — backend does INSERT, returns { id: UUID }
//   UUID   = existing assessment — backend does UPDATE

const result = await apiService.saveAssessment(formData);

// On first save: store the returned UUID
if (!formData.assessmentId && result?.id) {
  confirmDbSave(result.id);  // re-keys localStorage and updates FormContext
}

Section D localStorage & State Management (FormContext) ✓ Completed
D1
The localStorage ArchitectureFile: /app/src/context/FormContext.jsx

The app uses a multi-assessment localStorage store. Every assessment gets its own slot. Users can have multiple drafts and the correct one is restored on page reload.

Two localStorage keys — all access goes through constants, never raw strings:

Key constantActual keyWhat it stores
LS_ASSESSMENTS_KEYiia_assessmentsObject: { [localId]: formDataSnapshot } — holds all drafts on this device
LS_ACTIVE_KEYiia_activeString: the localId of the assessment currently being edited

Local IDs vs Database IDs:

// Before first DB save:
localId = "local_1716900000000_ab3f2"  // our generated key
assessmentId = null                     // no DB record yet

// After first successful DB save:
localId = "550e8400-e29b-41d4-..."    // re-keyed to the DB UUID
assessmentId = "550e8400-e29b-41d4-..."  // same value
D2
Auto-Persist — Every Change Saved Automatically

A useEffect inside FormContext watches formData and writes it to localStorage on every change. Users never lose data even if the browser crashes.

// Inside FormContext.jsx — runs on every formData change
useEffect(() => {
  if (formData.localId) {
    writeAssessmentToStore(formData.localId, formData);
    // Also stamps lastSavedAt: new Date().toISOString()
  }
}, [formData]);
Key principle
localStorage is always written first. The database is a background sync. If the backend is unavailable, the user never notices — their data is always safe locally.
D3
FormContext Methods Reference
MethodWhat it doesWhen to use
updateFormData(data)Shallow-merge into top-level formDataUpdating common fields (title, leadName etc)
updateFormSection(type, section, data)Update a specific nested sectionUpdating form1.welshLanguage etc
commitStep(stepIndex, data)Merge data + mark step complete in one pass. Returns the exact merged snapshot for DB save.Every handleNext — use this instead of updateFormData + completeStep
confirmDbSave(assessmentId)Re-keys localStorage from localId to real DB UUID. Prevents duplicates on future saves.After first successful saveAssessment() call
loadAssessment(dbResponse)Populates FormContext from a DB row. DB column values always override stale form_data values.When user opens an existing assessment from workspace
resetFormData()Creates a new blank assessment with a fresh localIdWhen user clicks "Start New Assessment"
startAssessment(formType)Sets form type on an active assessment. Creates new slot if none exists.FormSelection page when user picks form1 or form2
deleteLocalAssessment(localId)Removes from localStorage. Clears active pointer if it was the current form.User deletes a draft from workspace
Critical — use commitStep not updateFormData in handleNext
commitStep returns the exact snapshot that was stored in one atomic operation. If you call updateFormData() and then pass formData to saveAssessment(), the formData reference is stale — React batches state updates, so completedSteps will always be one step behind in the database. Always use commitStep in step navigation handlers.

Section E Auto-Save & Save Button ✓ Completed
E1
How Auto-Save Works on Step Navigation

Every time a user clicks Next or Back in a form step, the current step's data is saved to both localStorage (instantly) and the database (background, non-blocking). The user is never blocked if the database is unavailable.

The pattern used in every form step's handleNext:

const handleNext = async () => {

  // 1. Build this step's data
  const updatedData = {
    title: formState.title,
    form1: { ...formData.form1, affectedGroups: formState.affectedGroups }
  };

  // 2. commitStep: merges data + marks step complete in ONE pass.
  //    Returns the exact merged snapshot — no staleness risk.
  const dataToSave = commitStep(0, updatedData);  // 0 = step index

  // 3. Background DB save (non-blocking — wrapped in try/catch)
  try {
    const result = await apiService.saveAssessment(dataToSave);

    // 4. On first successful DB save: re-key localStorage to real UUID
    if (!formData.assessmentId && result?.id) {
      confirmDbSave(result.id);
    }
  } catch (err) {
    // Silent fail — data is safe in localStorage
    console.warn('[AutoSave] Could not save to database:', err.message);
  }

  // 5. Navigate regardless of DB save result
  navigate('/form1/step2');
};
Why silent fail is correct here
localStorage was written in step 2 before the DB call. The user's data is safe. Blocking navigation on a network failure would be a bad experience. The next step navigation will attempt another DB save.
E2
Manual Save ButtonFile: /app/src/components/ui/SaveButton.jsx

Appears in the Header during any active form. Allows users to manually trigger a database sync at any time. Always reports success because localStorage always succeeds.

Save states: idle → saving → saved (2 seconds) → idle

// SaveButton behaviour:
onClick = async () => {
  if (!formData.formType) return;  // Nothing to save

  setSaveState('saving');

  try {
    const result = await apiService.saveAssessment(formData);
    if (!formData.assessmentId && result?.id) {
      confirmDbSave(result.id);  // First DB save — upgrade localStorage key
    }
  } catch (err) {
    // Silent — localStorage already saved. DB sync will happen next time.
    console.warn('[SaveButton] DB save failed. Data safe in localStorage.', err.message);
  }

  // Always show 'Saved ✓' — localStorage always succeeded
  setSaveState('saved');
  setTimeout(() => setSaveState('idle'), 2000);
};
Important design decision
The button always shows "Saved ✓" regardless of whether the DB call succeeded. This is intentional — localStorage saved successfully. The DB failure is an implementation detail the user does not need to know about. The data is safe.
E3
The Two-Phase Save Model — Summary
Phase 1 — Immediate (always succeeds): User types or clicks Next ↓ FormContext useEffect fires ↓ writeAssessmentToStore(localId, formData) ↓ localStorage updated ✓ Phase 2 — Background (best-effort): handleNext or SaveButton calls apiService.saveAssessment() ↓ Backend receives POST /api/saveAssessment ↓ If assessmentId is null → INSERT → returns { id: UUID } If assessmentId is UUID → UPDATE → returns { id: UUID } ↓ confirmDbSave(id) re-keys localStorage entry to real UUID ↓ Future saves will UPDATE not INSERT ✓
E4
Read-Only Enforcement (Signed-Off & View-Only)

Every form step checks two conditions before rendering inputs as editable:

// At the top of every step component:
const isReadOnly = formData.status === 'signed_off'
                || formData.userRole === 'view';

// Applied to all inputs:
<input readOnly={isReadOnly} ... />
<textarea readOnly={isReadOnly} ... />

// Navigation buttons hidden when read-only:
{!isReadOnly
  ? <NextButton onClick={handleNext} />
  : <button onClick={() => navigate('/')}>Back to My Assessments</button>
}
When read-only is applied
signed_off — assessment permanently locked after sign-off. view — user was shared the assessment with view-only permission (userRole set by loadAssessment from the DB response).

Section G How to Develop — Adding New API Calls & Form Steps
G1
Adding a New API Method to api.js

Follow the existing pattern. Choose Pattern A (user-facing error) for most calls. Use Pattern B (silent fail) only if the caller handles failure without showing the user anything.

// Pattern A — user-facing error (use for most new methods)
myNewEndpoint: async (param) => {
  try {
    const response = await fetch(`${API_BASE}/myEndpoint`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ param }),
    });
    return await handleResponse(response);
  } catch (error) {
    handleError('My endpoint', error);  // throws user-friendly message
  }
},

// Pattern B — silent fail (only when caller swallows the error)
myBackgroundCall: async (data) => {
  const response = await fetch(`${API_BASE}/myEndpoint`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(data),
  });
  return await handleResponse(response);  // raw error propagates to caller
},
G2
Adding a New Form Step

Every form step follows the same structure. Copy an existing step and follow this checklist:

  1. Import: useFormContext, apiService, commitStep, confirmDbSave
  2. Add const isReadOnly = formData.status === 'signed_off' || formData.userRole === 'view'
  3. Initialise local state from FormContext values (so data survives navigation)
  4. In handleChange: call updateFormData() immediately so SaveButton always has current data
  5. In handleNext: call commitStep(stepIndex, updatedData) — not updateFormData — to get the snapshot
  6. Pass the snapshot to apiService.saveAssessment(dataToSave) — not the stale formData
  7. Call confirmDbSave(result.id) on first successful save (when formData.assessmentId is null)
  8. Wrap DB call in try/catch with console.warn on failure — never block navigation
  9. Apply readOnly={isReadOnly} to all inputs and textareas
  10. Hide Next button and show "Back to My Assessments" when isReadOnly
// Minimal correct handleNext pattern:
const handleNext = async () => {
  const updatedData = {
    form1: { ...formData.form1, myField: formState.myField }
  };
  const dataToSave = commitStep(STEP_INDEX, updatedData);
  try {
    const result = await apiService.saveAssessment(dataToSave);
    if (!formData.assessmentId && result?.id) {
      confirmDbSave(result.id);
    }
  } catch (err) {
    console.warn('[AutoSave] DB save failed:', err.message);
  }
  navigate('/form1/stepN');
};
G3
Adding a New Field to FormContext
  1. Add the field with its default value inside getInitialState()
  2. Because of deepMerge, old saved sessions will automatically get the default value on next load — no migration needed
  3. The field will be included in every saveAssessment call automatically since the whole formData object is sent
  4. The backend stores everything in the form_data JSONB column — no schema change needed for new form fields
G4
How the Workspace Page Works — listAssessments, loadAssessment & deleteLocalAssessment

The workspace (LandingPage.jsx) is the home screen after login. It combines three systems: the API service, FormContext, and localStorage. Understanding how they interact is important for anyone maintaining or extending it.

On mount — fetch all assessments:

useEffect(() => {
  const fetchAssessments = async () => {
    try {
      const data = await apiService.listAssessments();
      setAssessments(data || []);
    } catch (err) {
      if (err.status === 401) {
        setError('You are not logged in. Please log in to see your assessments.');
      } else {
        // Fallback: show local-only drafts from localStorage if DB is unavailable
        const store = readAssessmentsStore();
        const localItems = Object.values(store);
        setAssessments(localItems);
      }
    }
  };
  fetchAssessments();
}, []);

Opening an existing assessment — two paths depending on source:

const handleOpenAssessment = async (assessmentId, formType, status) => {

  // Path A: DB-backed assessment (assessmentId is a real UUID)
  if (assessmentId && !assessmentId.startsWith('local_')) {
    const data = await apiService.getAssessment(assessmentId);
    loadAssessment(data);  // populates FormContext from DB row
    navigate(formType === 'form1' ? '/form1/step1' : '/form2/step1');
    return;
  }

  // Path B: Local-only draft (assessmentId starts with 'local_')
  // Load directly from localStorage — no DB call needed
  const store = readAssessmentsStore();
  const localData = store[assessmentId];
  if (localData) {
    loadAssessment({ id: assessmentId, form_data: localData,
                     status: localData.status, form_type: localData.formType,
                     user_role: 'owner' });
    navigate(formType === 'form1' ? '/form1/step1' : '/form2/step1');
  }
};

Deleting an assessment — two steps in the correct order:

const handleDelete = async (assessmentId) => {

  // Step 1: Remove from localStorage immediately (always succeeds)
  deleteLocalAssessment(assessmentId);
  setAssessments(prev => prev.filter(a => a.id !== assessmentId));

  // Step 2: Sync deletion to DB in background (silent fail — Pattern B)
  if (assessmentId && !assessmentId.startsWith('local_')) {
    try {
      await apiService.deleteAssessment(assessmentId);
    } catch (err) {
      // Silent — localStorage already cleaned up. DB will eventually
      // be cleaned by the backend if the record is orphaned.
      console.warn('[Delete] DB delete failed:', err.message);
    }
  }
};
Key pattern to remember
localStorage always changes first. The DB call is always a background sync that can silently fail. This pattern is consistent across save, delete, and complete — the user never sees a failure caused by the backend being unavailable.

Starting a new assessment from the workspace:

const handleStartNew = () => {
  resetFormData();          // Creates fresh localId, stamps createdAt

Reference Troubleshooting
!
Cannot GET /api/hello or CORS errors
  1. Verify /api is running: cd api && npm start
  2. Check vite.config.js has the proxy section
  3. Use swa start instead of npm run dev for full-stack testing
!
Auth endpoint not available / "user is undefined"
  1. Create .env.local from the template: cp .env.example .env.local
  2. Set VITE_USE_MOCK_AUTH=true for npm run dev
  3. Set VITE_USE_MOCK_AUTH=false for swa start
  4. Restart the dev server after changing .env.local
!
localStorage data not persisting
  1. Check that formData.localId is set — auto-persist only fires when localId exists
  2. Call startAssessment(formType) or resetFormData() before trying to save — these create the localId
  3. Check DevTools → Application → Local Storage for iia_assessments and iia_active keys
!
DB save returns wrong assessmentId / duplicates appearing
  1. Verify you are calling commitStep() not updateFormData() in handleNext
  2. Verify you are passing dataToSave (the commitStep return value) to saveAssessment() — not the stale formData
  3. Verify you are calling confirmDbSave(result.id) after the first successful save
!
swa: command not found
npm install -g @azure/static-web-apps-cli
!
Port 7071 already in use
